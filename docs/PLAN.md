# Mathnim 工程方案

2026-09-30 制定。这份文档列出下一阶段要做的全部工程工作：目标、架构、工作包、顺序、估算和风险。每做完一项就在这里更新状态。

## 0. 已定的决策

| 项目 | 决定 |
|---|---|
| 两种教学模式 | **高中：游戏式**。数学本身就是玩法，学生持续动手，靠关卡目标推动。**大学：3b1b 式**。用可视化解开关键困惑，同时展示图形能力。 |
| 大学 demo | 特征值与特征向量，接着直接讲 PCA |
| 高中 demo | 把现有的披萨课重做成闯关式 |
| 学生提问 | 按学生个人情况生成文字加可交互画面；**体感延迟上限 8 秒** |
| 模型 | DeepSeek，**默认 `deepseek-flash`**；`deepseek-v4-pro` 用于离线或后台的难题；Anthropic 保留为可选。所有模型都在服务器端持有 key。 |
| 画面主题 | **所有课统一用浅色主题**（2026-10-10 用户决定："主题要和其他题统一，以后都用这个主题"）。不做深色课，也不做主题切换。 |

### 基线（2026-09-30）

- manim-web：用 Manim 文档里的 395 个例子与真 Manim 对比，结果是 337 通过、29 轻微差异、0 失败、9 已知差异、20 跳过。
- 其他检查：lesson_doctor 33/33 通过；类型检查和单元测试全部通过。
- 已有三节课：披萨课（15 分钟）、最佳射门角度、圆周角（AI 生成，已录制可离线回放）。
- 提问流程：生成场景代码 → 在隔离环境运行 → 排版检查 → 数值验算 → 自动修复。
- DeepSeek 已接入：服务器代理持有 key，浏览器只能看到"有没有配置"，看不到 key 本身。

### DeepSeek 实测（2026-09-30）

| 请求 | 模型 | 耗时 | 结果 |
|---|---|---|---|
| 一句话回答 | flash | 1.3 s | 正确，含约 100 个推理 token |
| 一句话回答 | v4-pro | 1.9 s | 正确 |
| 完整回答：从零写场景代码（"为什么行列式是面积缩放倍数"） | flash | **生成约 72 s，验证 1.3 s** | 第一次尝试就通过检查，数学正确，带滑块；但文字偏长，滑块提示标签超出了画布边界 |
| 同上 | v4-pro | 超过 67 s 仍未返回（被页面刷新中断） | 不适合实时使用 |

**结论：** 从零写代码的方式离 8 秒差一个数量级。8 秒只能靠两点实现：文字先行，加上"选用现成零件、填参数"。从零写代码只作为后台兜底。

## 1. 架构：分层与解耦

```
L4 应用层        学生群体（高中 / 大学）→ 课程目录、默认模式；主题（用户自选）
L3 呈现层        游戏呈现（关卡、星级、地图、角色、手感）｜叙事呈现（章节、可拖动的公式数字、联动视图、推导）
L2 内容与学习核心 内容单元、推进规则、语义事件与误区识别、评分、学习者模型、事件日志、旁白数据   ← AI 只生成这一层
L1 交互工具包     拖动与吸附、切割、盖章、拖数字改值、字块、数轴估计、约束、操作提示、可观察状态值
L0 manim-web     Manim API、渲染、时间线、TeX、3D（不含任何教法）
```

### 1.2 关键接口（草案）

```ts
// L1 -> L2：交互只报告有意义的事件，不关心教法
interface SemanticEvent { type: string; data?: Record<string, unknown>; t: number }  // 例：'slices_changed' {n: 24}；'det_zero'
interface Detector { id: string; on(e: SemanticEvent, world: WorldState): Finding | null }  // 例：误区"把直径当半径用"
interface Finding { kind: 'goal' | 'misconception' | 'progress'; id: string; evidence?: string }

// L2：内容单元（可序列化，AI 可以生成）
type Unit =
  | { kind: 'scene'; id: string; scene: SceneRef; narration?: Line[] }
  | { kind: 'world'; id: string; world: WorldRef; goals: Goal[]; detectors?: string[]; narration?: Line[]; stars?: StarRule[] }
  | { kind: 'check'; id: string; question: Question; narration?: Line[] };
interface Line { text: string; when: 'enter' | 'idle' | { event: string } | { finding: string }; style?: 'playful' | 'calm' }

// L2 -> L3：推进规则可以替换
interface FlowPolicy { next(state: FlowState, f: Finding | null): FlowAction }  // 游戏：挑战 -> 失败反馈 -> 重试 -> 过关；叙事：章节加可选探索
interface Presenter { mount(host: HTMLElement): void; show(unit: Unit, ctx: PresentCtx): void; react(f: Finding): void; unmount(): void }

// 可视化零件：参数化、事先验证过；可以新建场景，也可以接着当前画布继续
interface Visual<P> {
  name: string; summary: string; params: JSONSchema; examples: P[];
  build(p: P): Scene;                     // 新场景
  apply?(on: Scene, p: P): Animation[];   // 在学生当前的画布上继续
  ids: string[];                          // 暴露给 AI、描述器、检查器的对象 id
}
```

### 1.3 原则

- **数学世界与教法分开。** manim-web 和交互工具包里不出现关卡、星星、分数。
- **靠事件和误区识别衔接。** 呈现层只订阅识别结果（进度、目标达成、误区），不直接读画面上的对象。
- **内容是纯数据。** 场景和世界通过引用指向代码（人工写的或零件），这样 AI 生成、检查、缓存都在同一层进行。
- **颜色只按名字引用。** 画面代码只写配色名称，不写具体颜色，为主题自选做准备。

### WP3 游戏呈现层与披萨闯关课 ✅
- **呈现层：** 全屏舞台（没有播放条），对话气泡和目标横幅，过关结算（星级），关卡地图，适配手机。
- **关卡：**

| 关卡 | 内容 |
|---|---|
| 0 下注 | 把硬币拖到 16 寸一个或 8 寸两个的一边 |
| 1 铺满 | 用半径方块盖住披萨，可以剪开方块，计数约 3.1 |
| 2 切与拼 | 划刀切片，拖动拼成一排，切得越细越接近长方形 |
| 3 拼出公式 | 把 r、π、× 这些字块拖进空格，拼出 πr² |
| 4 面团机 | "做一个芝士正好两倍的披萨"，按精度给星 |
| 5 高峰时段 | 按客人点的面积出餐，算利润；把直径当半径用会直接亏钱 |
| Boss | 把 4 个小披萨的芝士倒进大披萨，验证开场的赌注 |

- **旁白：** 约 60 句短反应，用 edge-tts 的 Andrew 声音预先生成。
- **验收：** 每 10 到 20 秒至少一次操作；每关都能通关，lesson_doctor 会检查；浏览器试玩。
- **估算：** 呈现层约 25 万，课程约 60 万。

### WP4 叙事呈现层与"特征值 → PCA"课 ✅
- **呈现层：** 章节式叙事（与其他课统一的浅色主题），段落中的数字可以拖动改值，多视图联动，推导的公式和图形同步高亮，任何画面都可以停下来自己探索。
- **课程骨架**（约 20 分钟；每段解开一个困惑，画面同时沉淀为 WP5 的零件）：

| 段落 | 解开的困惑 | 学生操作 |
|---|---|---|
| 1 矩阵是对空间的运动 | "矩阵是一张数字表" | 拖动 î 和 ĵ 的落点，网格实时变形，矩阵数字同步变化 |
| 2 行列式 | "det 只是个计算公式" | 把两个基向量拖到共线，方格塌成线，det 变成 0；翻转时 det 变负 |
| 3 找不被转向的方向 | "特征向量是什么" | 转动探测向量，它和 Av 一起画出轨迹，两者对齐的瞬间高亮 |
| 4 为什么是 det(A−λI)=0 | 核心困惑 | 拖 λ 滑块，λ 碰到 det 曲线零点的那一刻，网格正好塌成一条线 |
| 5 旋转与复数特征值 | "为什么有时解出复数" | 把矩阵拖成旋转，特征线消失，向量场开始绕圈 |
| 6 反复作用 | "学它干嘛" | 反复作用 Aⁿv，看向量被甩向主特征方向；换到特征基下，Aⁿ 变成简单的伸缩 |
| 7 对称矩阵 | "为什么 PCA 能用特征向量" | 对称矩阵的特征向量正交，把单位圆变成椭圆，主轴就是特征向量 |
| 8 数据的形状 | "方差和协方差是什么" | 拖动数据点，协方差椭圆跟着变，矩阵实时更新 |
| 9 散得最开的方向 | PCA 的核心：为什么是协方差矩阵的特征向量 | 转动一条投影线，投影点的方差实时显示；方差最大的那一刻正好对齐协方差的主特征向量 |
| 10 降维 | "降维丢掉了什么" | 3D 点云投影到前两个主成分，旋转视角对比；另附一个真实数据例子（身高体重，或手写数字） |

- **验收：** 每段都有明确的"原来如此"时刻，并有一个可操作的检验；在浏览器里完整走一遍。
- **估算：** 呈现层约 20 万，课程约 45 万（PCA 部分使课程增加约三分之一）。

### WP6 个性化 AI 回答（8 秒方案） ✅

**时间预算：**

| 时刻 | 学生看到的 |
|---|---|
| 0–0.3 s | 问题回显；画布上本地高亮与问题相关的对象（按关键词匹配对象 id） |
| ≤ 1.5 s | 第一批文字出现（flash 流式输出，提示词短） |
| ≤ 4 s | 2 到 4 句文字说完 |
| **≤ 8 s** | 画面开始播放：flash 输出一份"画面方案"（选零件、填参数），本地校验并渲染 |
| 8 s 以后（少数情况） | 零件覆盖不到的问题：先给文字和最接近的零件画面，同时在后台从零写代码（30–90 s）。写好后替换画面，并存入缓存和候选零件 |

**调用设计：** 两个 flash 请求并行发出，共享同一个可缓存的前缀（DeepSeek 会自动缓存重复的提示词前缀）。
- A：诊断学生困惑，再流式输出文字。
- B：只输出"画面方案" JSON：
  - 诊断结果；
  - 在当前画布上继续，还是另起一个场景；
  - 步骤列表：每步包括零件、参数、要高亮的对象、配套的一句话；
  - 留给学生操作的交互；
  - 一个检验问题。

**上下文（控制在约 3K token）：**
- 学段与模式；
- 当前画面：精简的对象列表、id 和数值；
- 所在的课和段落；
- 掌握度和出现过的误区；
- 最近 3 轮问答；
- 语言。

**校验（本地，< 0.5 s）：**
- 方案 JSON 符合格式，参数在允许范围内；
- 在隔离环境里空跑一遍，做排版检查；
- 文字里的数字自动验算。

**降级顺序：** 零件方案 → 只给文字加最接近的零件 → 后台从零写代码。

**个性化的依据：** 学生的误区、掌握度，屏幕上他正在看的对象，他问过的问题。回答后的检验题结果也回写进学习者模型。

**需要先确认的技术点：**
- DeepSeek 能否关闭推理以进一步降低延迟；
- flash 生成画面方案的准确率（用少量实际提问和浏览器验证）。

**指标：**
- 首字延迟、文字完成时间、画面出现时间，各看 p50 和 p95；
- 画面方案一次通过率；
- 学生点"有用"的比例。

**估算：** 约 40 万。

## 5. 风险

| 风险 | 应对 |
|---|---|
| flash 生成画面方案的准确率不够 | 用实际提问检验；零件参数写得保守、有默认值；难题交给后台 v4-pro |
| 推理耗时吃掉 8 秒预算 | 尝试关闭推理；提示词短并复用缓存前缀；把"画面方案"做成小 JSON |
| 零件覆盖不到学生的问题 | 后台从零写代码兜底，生成结果进入缓存和候选零件，由人工审核后加入零件库 |
| 触屏上的拖动与切割体验 | WP1 每种交互都在手机尺寸下实测 |
| edge-tts 是非官方接口 | 仅开发期使用；上线改用 Azure 语音服务 |
| 游戏课的内容制作成本高 | 交互方式和零件复用；AI 生成 v2 课程作为初稿，人工打磨 |
