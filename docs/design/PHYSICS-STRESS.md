# 物理压力测试：引擎能不能撑起一门物理课（2026-11-06）

问题（Lucas）：新的图形引擎 `packages/engine` 能不能做物理课？做法：做三张专门找毛病的图，引擎里缺的、而且任何以后的图都会要的，
就加进引擎（带测试）；物理本身放在包里的小模块里（像 `mgmt/lp2d.ts`）。不用任何物理库或 3D 库。

**结论先说**：二维、由参数驱动的图本来就行；三个怀疑的缺口都是真的，前两个现在补上了，第三个（3D）补到"矢量和简单刚体够用"为止。

| 怀疑的缺口 | 结果 |
|---|---|
| 没有模拟循环（脚本是时间的纯函数，`over()` 只是拉长一步，不是积分器） | 真的。加了 `Sim`（`sim.ts`）：固定步长、可选积分器、状态是"输入 + 时间"的纯函数，所以和时间线的回放、跳转天然一致；探索时播放器按真实时间推进；手柄可以"按住—松手" |
| 只有标量场 `Field`，没有矢量场、没有场线 | 真的。加了 `VectorField`（箭头网格）、`streamline()`（RK4 流线）、`Path` 的 `heads`（线上的箭头） |
| 3D 太少（`View3D`：点、线、箭头、面、轨道；没有光照、没有实体） | 真的。加了实体杆 `bar()`（背面剔除 + 一盏灯的平光照）、`pieces` / `bias` 让画家算法在"线穿过实体"时排对、`show` 逐个出场、`target` 相机看向哪、`px()` 给 3D 点贴标签、`handle3d()` 在屏幕平面或沿一条线拖一个 3D 点。仍然没有深度缓冲 |

怎么打开（不在任何列表里）：开发服务器上 `/course-physics-stress/physics-stress-figures`，`?step=pendulum`、`?step=charges`、`?step=torque`
是三页。这是一门隐藏的演示课：`apps/mathnim/public/demo/courses.json` 里的条目带 `hidden: true`（`studio_courses.ts` 新增的字段，首页按它不列出），
课由 `docs/lessons/physics-stress/build.py` 生成。三张图在 `packages/visuals/src/physics/`（包 `@mathnim/visuals/physics`），
没有加进导师的目录（`apps/mathnim/tools/catalog.ts` 没有导入它，也没有跑 `npm run catalog`），所以 AI 也不会选到它们。

量数的条件：这台 Mac，无头 Chrome（`--disable-gpu`，所以 `Field` 走的是 CPU 档：半分辨率算再放大），DPR 2；"降速 4 倍"是 CDP 的 CPU 节流。
帧时间是页面里每个 `requestAnimationFrame` 回调的耗时（播放器在回调里画），拖动用真实鼠标事件，60 次移动、每 16 ms 一次。同一测量跑几次会差
30–50%，下面给的是几次的范围。截图在 `docs/design/physics-shots/`。

## 1. 积分出来的单摆 `phys_pendulum`

把摆锤拉到某个角度再松手，按 θ″ = −(g/L) sin θ（可选阻尼 −cθ′）一步一步算，旁边是小角度模型 θ″ = −(g/L) θ（紫色虚线）。右边是
角度—时间曲线（10 秒一扫）、势能和动能（一根以松手时能量为全长的条）、精确周期和 2π√(L/g)。可选频闪：过去一秒里每 0.1 秒一个影子
（Marey 的连续摄影），慢的地方挤在一起。物理在 `physics/pendulum.ts`（精确周期用算术几何平均）。

截图：`pendulum-desktop.png`、`pendulum-phone.png`（120°，探索中继续摆）、`pendulum-170-strobe-desktop.png`（170° 加频闪）、
`pendulum-released-175-phone.png`（手机上拖到 −175° 松手：真实单摆在顶端停留很久，T = 5.77 s，模型 2.01 s）、
`sheet-pendulum-170-strobe.png`（检查器的样张，宽屏和手机）。

**引擎做得好的**：状态 / 派生、行列排版（手机自己一套组合）、读数、lint、doctor 都直接能用；杆、摆锤、曲线、能量条、频闪全是现成的
`Path` / `Marker` / `Region` / `Dots`。最关键的是"脚本是时间的纯函数"这条设计本身：只要模拟的状态也是纯函数，它就自然放进时间线，
不用改时间线。

**缺的**：
- 没有积分器。`call(dur, f)` 要求 f 只依赖进度 u，硬做就是每帧从 0 重新积分，代价随时间线性增长。
- 探索时时间不会走：活的播放器只在参数被写的时候才画。
- 脚本没有"再跑 9.6 秒"这种相对的一步（`set` 只能设到绝对值）。
- 手柄只能把指针映射成 (x, y)，不能"沿着圆"（摆锤的角度）。
- 手柄不能"按住一个正在跑的东西"。

**加了什么（为什么是通用的）**：
- `Sim`（`sim.ts`，281 行）：`fig.sim({ inputs, start, accel | deriv, method, dt, max_t })`。二阶系统（q″ = a(q, q′, t)）用
  `'verlet'`（速度 Verlet，默认）、`'euler'`（半隐式 Euler）或 `'rk4'`；一阶系统（y′ = f）用 `'rk4'` 或显式 `'euler'`。
  - **确定性是构造出来的**：第 n 步的状态永远是从第 0 步按同一串运算算到的；检查点（默认每 0.25 秒）就是这条路上的状态，所以
    无论顺着播、往回跳还是重放，同一时刻得到逐位相同的数。跳转最多积分一个检查点间隔（60 步）。
  - `sim.state` 是"时钟下的状态"（派生值），`sim.at(t)`、`sim.series(t0, t1, every)`（画曲线、频闪用，不动缓存）。
  - **输入一变就开始新的一轮**（时钟回到 0）：Sim 监听 `inputs` 读到的参数（穿过派生值），键盘微调、导师的 `set` 也一样。
  - `hold_with(handle)`：按住时这一轮停在起点（手柄设定起始状态），松手就从那里开始跑——"拖到某处再放开"。
  - 任何"会自己动"的图都要这个：弹簧、轨道、种群、RC 电路、投射运动。
- 播放器（`player.ts`）：活模式下，正在跑的 Sim 按真实时间推进（整步推进、余数留到下一帧；一帧最多 0.1 秒，后台标签页回来是慢下来不是跳）；
  没有在跑的就一帧都不画，和原来一样。
- 脚本：`run(sim, s)`（内部是 `set` 加了一个相对的 `by`），意图 `simulate`（外观表新增：匀速，减少动态效果时**保留**时长，因为运动就是内容）。
- `Handle` 的 `to: (d) => [θ]`：把指针所在的数据点映射成参数（圆上的角、曲线上的位置）；`fig.handle` 也接受 `at`、`to`、`r`、`look`。

**量到的**：
- 能量漂移（速度 Verlet，dt = 1/240 s，60 秒，每一步都算）：真实单摆 2.8×10⁻⁵ ~ 4.3×10⁻⁵（相对值，即 0.003%–0.004%），
  释放角 5°–175°；小角度模型 4.3×10⁻⁵。要求是 0.1%。`fig.check` 和测试都在查。
- 对比：同样步长的 RK4 在 120° 漂移 6.4×10⁻¹⁰，但一分钟要 8.7 ms（Verlet 1.1 ms），而且能量没有界（会慢慢漂）；半隐式 Euler 0.54%，
  这个步长下过不了 0.1%。所以长时间跑在探索里的，默认 Verlet 是对的。
- 周期：从模拟的过零点量出来的周期和精确值相对误差 ≤ 7×10⁻⁶（120°：2.75408 / 2.75409 s；175°：5.77280 / 5.77278 s）。
- 确定性：逐帧播到 20 s、跳回 5 s 再跳到 20 s、新建一个 Sim 直接到 20 s，三者逐位相同（`fig.check` + `sim.test.ts`）。
- 代价：两个单摆一分钟（14 400 步）1.1 ms；已经跑到 600 s 之后跳到 312.345 s：23 步。
- 页面里拖摆锤：桌面 p95 3.0 ms（降速 4 倍 8.1 ms），手机 0.9 ms（3.1 ms）；松手后摆动中每秒约 60 帧、每帧约 1 ms（降速 4 倍 2.3 ms）。
- 检查器：16/16 通过，单摆五个样例 0 警告，活帧 0.4–0.7 ms（node）。

**还缺的**：
- 跑到一半改一个常数（"现在打开阻尼"）只能重开一轮，因为一轮的轨迹只属于它的输入。要做，就把"在 t 时刻改了什么"作为输入的一部分
  （一个事件表）；这样学生的每次干预也能重放。没做。
- 探索里学生跑出来的那一轮不在时间线上：回放脚本会回到脚本那一轮。它可以由松手的角度重现（`report` 里有），但没有"记下来再放一遍"。
- `Sim` 不是 Thing：`describe()`、导师的手（`manifest_of`）看不到它，导师不能播放 / 暂停 / 松手（只能通过手柄的参数设释放角）。
- 没有自适应步长、没有隐式积分器（刚性系统：很硬的弹簧、近距离的轨道会要）。刻意没做。
- doctor 只在脚本的段落结尾和手柄的角上 lint；探索里跑起来之后的状态没人查。

## 2. 可以拖的点电荷 `phys_charges`

两三个点电荷（正负和大小由预设给），电势是底色（正红负蓝，两张 GPU 场）加等势线，电场画成箭头网格，也画成用 RK4 追出来的电场线，
每个电荷的条数和它的电量成正比；拖电荷时一切跟着走。物理在 `physics/electro.ts`：V 和 E 用同一个软化长度，所以 E 正好是被画出来的那个 V 的负梯度。
场线的种法：每个正电荷周围等角度种 round(8|q|) 条，沿 E 追到负电荷或边；某个负电荷收到的不够它的份额，就从已到达的线之间最大的空隙里
反向追（从远处来的线），并把这些线掉头，让所有线都顺着 E 走。

截图：`charges-desktop.png`、`charges-phone.png`（+2q、−q、−q）、`charges-dragged-desktop.png`、`charges-dragged-phone.png`（把 +2q 拖过去之后）、
`sheet-charges-triple.png`。

**引擎做得好的**：`Field` 一个公式三档（WebGPU / WebGL2 / CPU）直接画出电势；`aspect: 'equal'` + `fill` 让手机上变成正方形、单位长度不变；
电荷用 `Drawn`（逃生口）自己画，手柄 `look: 'none'`，探索时电荷外面一圈玻璃环；标签贴在点上；lint 抓住了几处问题。

**缺的**：矢量场；流线；路径上的方向箭头；`Field` 只有一种颜色，有正负的电势只能用两张场（两次 GPU 绘制），等势线也只能和底色同色。

**加了什么**：`VectorField`（`vectors.ts`）：箭头间距按 CSS 像素，所以手机上是更少的箭头而不是更小的箭头；`scale: 'unit'` 时箭头等长、强弱放在透明度里
（1/r² 的场跨好几个数量级，按长度画要么全是点、要么全交叉），`'linear'` 时长度随强度；按透明度分 6 桶，一桶一次描边。`streamline(f, seed, …)`：
每一级都归一化的 RK4（步长就是距离），在边上精确截断、停在 `stop`、停在驻点、回到起点算闭合。`Path` 的 `heads: [份额]`。都是任何"场"的图会要的
（流速场、斜率场、梯度）。

**量到的**：
- 垂直：四个预设里场线和等势线（V = ±0.25、0.5、1、2、4）的 52–156 个交点，偏离直角最多 0.21°–0.93°，平均 0.06°–0.15°（要求 2°）。
- 条数和电量：`like`、`unequal`、`triple` 每个电荷碰到的线正好是 round(8|q|)（16/8、16/8/8）；`dipole` 的 +q 碰到 9 条（−q 的一条反向线回到了 +q），
  在检查允许的 ±1 之内。偶极子从 +q 出发的 8 条里 4 条落到 −q，另外 4 条绕得比 8 × 6 的窗口还大、出了边——三维偶极子本来如此。
- 页面里拖电荷（CPU 档的场）：三电荷桌面 p95 4.4–5.7 ms，降速 4 倍 20–24 ms，最长 6.5–15.5 ms；偶极子桌面 3.3 / 16.5 ms；三电荷手机 2.3–3.1 / 8.3–14.9 ms。
  松手后 0 帧。
- 一帧花在哪（node，670 × 376，DPR 2，CPU 档）：两张场各 1.7 ms，场线 2.3 ms（其中追线 1.35 ms：22 条、2789 个点），箭头 0.45 ms，共 8.9 ms。
  在有 GPU 的机器上场几乎不花时间，场线成了主要开销。

**还缺的**：
- 有正负的（发散色）`Field`，以及颜色独立于底色的等势线。要改三档着色器，这里没有 GPU 可验证，所以没动，用了两张场。
- 场线是"平面里画三维的场"：在平面里等角度出发是课本的画法，线的疏密只是大致反映场强（只有在三维里才精确）。图下的说明里没写这一句。
- 种线的方法在包里，是电荷专用的；通用的"均匀流线"（Jobard–Lefer 那种）没做。
- 反向追的线在脚本里是从边上往电荷画的（线都顺着 E），看起来有点怪；需要一个"从哪头开始画"的选项。
- 电荷数多（五个以上）或步长更细时，每帧在主线程上重追场线会紧；到时候要缓存或放 worker。

## 3. 三维里的力矩 `phys_torque`

一根绕支点的刚性杠杆，力作用在杆上某点，r 从支点指向作用点，力矩 τ = r × F 从支点沿转轴画出，带右手定则的弯箭头和 r、F 张成的平行四边形
（面积就是 |τ|）。学生可以转视角、在屏幕平面里拖力的箭头、沿杆滑动作用点。矢量在 `physics/torque.ts`。

截图：`torque-desktop.png`、`torque-phone.png`、`torque-force-dragged-desktop.png`（把 F 拖到后下方：τ 翻到下面，弯箭头跟着反向）、
`torque-orbited-desktop.png`（转视角之后）、`sheet-torque.png`。

**引擎做得好的**：相机、投影、轨道手柄；相机角是参数，所以脚本能转视角；`fig.label` 的锚点可以是一个函数，直接用 3D 点投影出来的像素。

**一开始缺的**：
- 深度只是画家算法，按每个图元的平均深度排。一条穿过实体的长线是一个图元，要么整条在前要么整条在后；面按中心排，在线的附近会排错
  （r 箭头躺在杆上时被杆的侧面"切"成虚线，截图里看到过）。
- 没有实体和光照：面只是半透明的淡色，杆看起来是一条扁带子。
- 没有给 3D 点贴标签的办法、没有 3D 拖动、相机只能绕原点转、条目不能一个个出场（条目不是 Thing）、标签不避开 3D 的线。

**加了什么**（都是可选的；原来的 3D 测试原样通过）：`line` / `arrow` 的 `pieces`（切成小段分别排序，箭头的头在尖上单独一段、大小按整支箭头算）；
`bar(from, to, { half, segments })` 实体杆（六个朝外的面，背面剔除，正面按一盏固定的灯做平光照：受光的面浅，背光的面深，像纸在光下；
长面切成 `segments` 段；分段的接缝用面自己的颜色描边，不露缝）；`face({ shade, cull })`；`bias`（排序时加在深度上：躺在面上的箭头画在面上面）；
`show`（一个参数当透明度，脚本可以一个个带出来）；`target`（相机看向的点，轨道绕它转）；`px(p)`、`px_per_unit()`、`screen_axes()`；
`Handle3D` / `handle3d()`：在屏幕平面里拖一个 3D 点，或者给 `along` 沿一条线拖（按这条线在屏幕上的投影算，透视缩短时点也一直在指针下面）；
`obstacles: true` 让标签避开 3D 的线、箭头和点。

**量到的**：
- `fig.check`："画出来的 τ 就是 r × F"：垂直于 r 和 F、长度 |r||F| sin θ、右手系（相对误差 1e-9），而且箭头尖在屏幕上的位置和独立算出的叉积投影相差 < 1e-6 px。
  五个样例 × 两种语言 × 手柄的角都通过。
- 页面里拖力的箭头：p95 2.4 ms（降速 4 倍 7.0 ms），最长 5.6 ms。**改之前**读数里的数字写在 TeX 里，同一个拖动是 6.1 ms（22.5 ms）——见第 4 节。
  转视角 p95 1.4–1.7 ms（4.0–4.8 ms）。松手后 0 帧。node 里 3D 场景本身一帧 1.0–1.4 ms（14 段杆 × 最多 4 个面、36 段转轴、几十段箭头和弯箭头）。

**还缺的 / 做不到的**：
- `pieces`、`segments` 只是让画家算法"大致对"，`bias` 是手调。相交的面（一个平面穿过实体）不切分面（BSP）或没有深度缓冲就画不对。
- 没有曲面实体（圆柱、球、锥），箭头的头是屏幕上的三角形（对矢量图来说够了）。
- 轨道手柄占满整个视图：手机上在图上竖着拖是转视角，不是滚页面。所有可探索的图在探索时都给画布设了 `touch-action: none`，但轨道占满全图让这件事躲不开。
- 手柄重叠时按"中心最近"选：力的手柄小、轨道的中心在图中间，所以能用；给手柄一个优先级（轨道最后）会更稳。
- 标签避让不知道深度：拖动中看到过 F 的标签被挤到离箭头尖约 100 px 的地方。
- 读数里数字（无衬线、等宽数字）和 TeX 符号（衬线）混排，见第 4 节的取舍。
- 手机上：图约 320 px 宽，标签 15 px、手柄触控区 44 px 都满足 lint；但"在屏幕平面里拖箭头"在没有悬停的手机上好不好懂，没有在真机上试过。

## 4. 三张图共同发现的

- **TeX 里的活数字很贵**。读数里写在 TeX 里的数字每变一次，MathJax 就重新排一次：每个读数每帧 1.5–3 ms（node：力矩的 F 读数 3.2 ms、|τ| 那行 2.2 ms；
  单摆的 θ₀ 2.0 ms、T 1.4 ms）。换成 `value` 部分（等宽数字、预留宽度）后每个 0.1–0.2 ms。会变的数字应该用 `value`；引擎里值得做一个
  "TeX 模板里留数字空位"或缓存数字字形的快路径，否则每张有活数字的物理图都会碰到。
- **会变宽的 TeX 读数会出界**：读数的宽度在排版时按当时的内容量；TeX 部分变宽（多一个负号、多一位数）就可能挤出图。只有检查器 640 px 的那一轮抓到了，
  doctor 的 960 / 360 两个尺寸没抓到。
- 跑起来的模拟每帧都画（每秒 60 帧），这是对的，但"静止时 0 帧"的承诺在单摆的探索里不成立：它一直在摆。可以考虑摆幅小到看不出时自己停（阻尼的情况），没做。
- 外观表新增名词：`bob`、`small-angle`、`kinetic`、`potential`、`energy`、`positive`、`negative`、`field`、`lever`、`lever-arm`、`force`、`torque`（正红负蓝，照课本）。
- 体积：三张图的包压缩后 27 KB（gzip 11 KB，含它引用的 `mpc/kit`）；引擎新增的 `sim.ts` + `vectors.ts` 压缩后 4 KB（gzip 1.7 KB）；
  内核源码从 4791 行到 5514 行（预算一万行）。没有引入任何库。

## 5. 建议

**做物理课之前要加的**（都不大）：
1. `Sim` 的事件表输入（"t 时刻推了一下 / 打开阻尼"），让学生的干预可以重放；再加上"记下学生的一轮、原样再放"（输入 + 时间就够）。
2. TeX 里活数字的快路径（或者在 README 写死规矩：活数字一律 `value`）。
3. 发散色 `Field` 和独立颜色的等势线（三档着色器都要改，需要在有 GPU 的机器上验证）。
4. 手柄优先级（轨道手柄最后被选中）。
5. 让 `Sim` 出现在 `describe()` / `manifest_of()` 里，给导师加 `play` / `pause` / `release` 这几个动作。

**可以等的**：自适应步长、隐式积分器（只有刚性系统要）、通用的均匀流线、把场线放到 worker、多体问题。

**`View3D` 能走多远**：矢量、坐标轴、箭头、刚性的杆和盒子、平行四边形、当作面的平面、小的多面体、转视角——也就是力学和矢量的图
（力矩、角动量、洛伦兹力、导线周围一圈圈的磁场箭头、叉积和右手定则）都够用，而且便宜（一帧 1–1.5 ms）。做不到的：光滑的曲面实体、相互穿插的面、
会自己挡住自己的网格曲面（比如把电势画成三维地形 V(x, y)）、阴影。建议 `View3D` 就停在"画布 + 分段的画家算法"；真要曲面时，像 `Field` 一样
单独做一个带深度缓冲的 GPU 网格（WebGL2 / WebGPU，CPU 档降级为分小块的画家算法），而不是把 `View3D` 越做越大。这也符合 `ENGINE.md` 第 11 节的
"不做物理引擎、不做通用 3D 引擎"：这次加的是一个几十行的积分器和几样 3D 的小工具，不是引擎。
